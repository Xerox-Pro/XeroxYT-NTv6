# Vercel使用量削減とショート推薦の改善

## 確認できた現状（2026-10-31 JST）

- Vercelプロジェクト: `xerox-yt-n-tv6`、本番リポジトリ: `Xerox-Pro/XeroxYT-NTv6`。
- 添付画面の直近30日: このプロジェクトがActive CPU 4時間48分、チーム全体の93.6%。これは請求額や停止日時を示す値ではない。
- 実画面の直近12時間: 約16,000呼び出し、CPU約10分。関数は `/server.ts` に集約され、APIごとのCPU寄与は現状の集計からは断定できない。
- 通常おすすめは最大12件の履歴詳細、10件の関連、追加5件の関連、最大4件の検索を取得する実装。失敗時の代替呼び出しを除いても最大31件に増える。
- ショートはサムネイル表示時に視聴済みを記録し、ランキングと通常候補を必ず交互に組むため、短い方の候補数で表示件数が切られていた。

## 今回の変更

### 1. 候補取得と並べ替えを分離

通常おすすめの公開候補は、履歴をページごとに4件、検索を最大3件に制限する。ローカル学習したキーワードを検索に実際に使い、履歴関連と新規トピックを両方返す。最終順位は既存の端末内推薦で決定する。YouTubeログイン時のホームフィード経路は維持する。

公開候補は15分・最大200キーのメモリキャッシュで再利用。同じ処理の同時要求は1つにまとめ、失敗はキャッシュしない。これは稼働中の同じインスタンスでの最適化であり、全リージョン共有・永続キャッシュではない。コールド起動でも正しく再取得する。個人のYouTubeフィードやセッションを共有キャッシュに入れない。

テストでは20件の履歴があっても初回は4件の関連＋3件の検索。同じ条件の同時・連続要求で追加取得は0件。旧実装の最大31件に対する外部取得回数の上限削減であり、料金の77%削減を保証する数値ではない。

ショートの取得も同時要求をまとめ、同じ解析済みフィードからの候補抽出を再利用する。選択済みの最大5ハッシュタグは1ページ2つずつ巡回し、すべての好みを保ちながら1回の処理を減らす。

### 2. 再生URL生成をCloudflareへ

既存 `xeroxyt-account` Workerに `/api/account/embed/:id` を追加し、Vercelの `/edu/:id`、`/scratch-edu/:id` とその `/api/` 版を転送する。

流れ: ブラウザ → Vercelの外部転送 → CloudflareのD1セッション照合 → 公開再生設定のキャッシュ → 再生URL。

Vercel Functionの実行とVercelから認証Workerへの往復を、このURL生成処理について省く。VercelへのHTTP要求・転送量自体は残る。CloudflareのWorker呼び出し・D1読み取りも残るので、無料化を保証しない。動画バイト列をこの新規経路に通す変更はしない。

セッションはキャッシュせず、毎回D1で失効を確認する。15分キャッシュするのは公開の埋め込み設定だけ。返却URLのホスト・パスは固定し、受信サイズは16KB、タイムアウトは5秒に制限。返却レスポンスは `private, no-store` と `CDN-Cache-Control: no-store`。有効なセッションを持つユーザーには従来と同じ再生URL形式を返す。Vercel内の旧URL生成処理はロールバック用に残す。

### 3. ショートの興味精度と多様性

- サムネイル表示や先読みだけで視聴済みにしない。表示中プレイヤーの再生イベントを確認して記録する。
- 実再生進捗、完了、繰り返し視聴、早いスキップから興味を自動推定。埋め込みが再生進捗を返さない場合、視聴時間を推測して学習させない。
- ショート画面の高評価・「興味なし」ボタンを削除。評価操作なしで学習し、アカウントごとの既存ローカルモデル内で保持する。
- ランキング候補と通常候補をまとめて採点。候補元を50:50に固定せず、片方が少なくても残りを活用する。
- 直近8件と重なる話題・投稿者に減点。5件に1件は探索を重視し、明確な不評を無視するランダム表示にはしない。
- 受動的な視聴信号は半減期7日、高評価など明示的な信号は従来の21日。古い視聴の偏りを弱める。
- `#shorts`、`#youtube`など識別力の低い語を学習特徴から除き、日本語の単語分割器を再利用する。
- 再生済みの先頭部分・現在の動画・先読み2件は位置を固定し、その先を並べ替える。
- 検索は検索語の範囲を守り、チャンネルページは投稿順を維持する。コメント・概要・標準再生操作も維持する。

これは限定環境で動く独自の軽量推薦。SNS各社の非公開モデル、他ユーザーの行動データ、映像・音声の意味解析を再現したものではない。好みの一致と多様性の改善を狙うが、「中毒性」や精度上昇はコードだけでは実証できない。Instagram/TikTok動画の無許可収集や転載は追加していない。

## 反映順序と検証

1. 修正ブランチのテスト・型チェック・ビルドを通す。
2. 既存Cloudflare Workerの現在の設定・D1バインドを保持したまま、追加エンドポイントを先に反映する。
3. 未ログインは401、有効セッションは再生URL、ログアウト後は401になることを確認する。
4. Vercelのプレビューで検索・通常おすすめ・ショートの移動・コメント・概要・チャンネル投稿順を確認し、その後に本番へ反映する。
5. 同程度のトラフィックで24時間以上比較する。VercelのActive CPU/1,000要求、関数呼び出し、転送量、4xx/5xx、CloudflareのCPU・D1読み取りを確認する。低トラフィックの時間帯だけを比べて削減率としない。
6. 推薦品質はスキップ率、完了率、10本中の投稿者数・話題数で評価する。視聴時間だけを成功指標にしない。新しい行動ログの外部送信は今回追加しない。

ロールバックはVercelを以前のデプロイに戻す。Cloudflareの新経路は追加のみなので、旧Vercelを壊さず残せる。問題がなければ高頻度の公開メタデータを別の共有候補ストアに移す次段階を検討する。今回の測定ではAPI別のCPU内訳が取れていないため、全APIを一括移行する根拠はない。
